# Cyber ETL + MLOps Pipeline: Suspicious Login Detection

An end-to-end, scalable data and machine-learning pipeline built for a PhD Data Science lab.
It extracts authentication events, an asset inventory and live vulnerability data. It
transforms them in parallel with Dask, loads a feature table into a relational warehouse,
then trains, tracks and registers a model with MLflow. The model is served with FastAPI,
monitored with Prometheus and Grafana, and the whole flow is automated with Apache Airflow
and GitHub Actions.

```
               ┌──────────── EXTRACT ────────────┐   TRANSFORM          LOAD              ML / MLOps
auth_events.csv ──(pandas, 50k-row batches)──┐
asset_inventory.db ──(SQLAlchemy)───────────┼──> Dask: clean ─> SQLAlchemy ─> MLflow: tune, ─> FastAPI ─> Prometheus
NIST NVD CVE API ──(requests, paging/retry)─┘    enrich,       warehouse    track, register  /predict    ─> Grafana
                                                  features,     (SQLite or   "champion"
                                                  normalize     PostgreSQL)
            orchestrated daily by Airflow  ·  tested, retrained and deployed by GitHub Actions
```

## Use case

Security teams must spot suspicious logins (credential stuffing, brute force, misuse of
privileged accounts) quickly. Each login event is enriched with the target asset's
criticality and the known vulnerabilities (CVEs) in its software. The model then scores how
likely the event is to be malicious.

| Source | Type | How it is extracted |
|---|---|---|
| `data/raw/auth_events.csv` (~300k rows) | Structured + unstructured (free-text log message, user agent) | `pandas.read_csv(chunksize=50_000)`: batch processing, written to Parquet parts |
| `data/raw/asset_inventory.db` | Relational database | SQLAlchemy query |
| NIST NVD CVE API 2.0 | Web API (JSON) | `requests` with paging, retries and rate limiting. Falls back to a generated offline sample (`data/sample/nvd_cves_sample.json`) when the API is unreachable |

> The login events and assets are **synthetic** (generated by `generate_data.py`), so no real
> user data is used. The offline NVD sample uses clearly fake IDs (`CVE-SAMPLE-…`). The live
> API is used whenever it is reachable.

## Project structure

```
├── src/cyber_pipeline/
│   ├── config.py           # all settings, overridable by environment variables
│   ├── logging_config.py   # console + rotating file logging, step timing
│   ├── generate_data.py    # creates the synthetic CSV + SQLite source data
│   ├── extract.py          # EXTRACT: CSV batches, SQLAlchemy, NVD API
│   ├── transform.py        # TRANSFORM: Dask cleaning, features, normalization
│   ├── load.py             # LOAD: SQLAlchemy -> warehouse (+ Parquet copy)
│   ├── train.py            # scikit-learn + MLflow tracking, tuning, registry, quality gate
│   ├── api.py              # FastAPI model service + Prometheus metrics
│   └── pipeline.py         # run everything from the command line
├── dags/cyber_etl_mlops_dag.py          # Airflow DAG (daily schedule)
├── .github/workflows/ci-cd.yml          # test -> train -> build & push image
├── monitoring/                          # Prometheus config, alert rules, Grafana dashboard
├── tests/                               # pytest: ETL, model, API, DAG
├── Dockerfile · docker-compose.yml
└── requirements*.txt
```

## Setup

```bash
git clone https://github.com/Zandubs0401/cyber-etl-mlops.git
cd cyber-etl-mlops
python3.11 -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
export PYTHONPATH=src                                     # Windows: set PYTHONPATH=src
```

Optional: `export NVD_API_KEY=...` (free key from nvd.nist.gov) raises the API rate limit.

## Run it

**1. Whole pipeline (generate data → ETL → train)**

```bash
python -m cyber_pipeline.pipeline            # uses the live NVD API
python -m cyber_pipeline.pipeline --no-api   # offline sample instead
```

**2. Experiment tracking**: `mlflow ui --backend-store-uri sqlite:///mlflow.db`, then open http://localhost:5000.
Each tuning session is a parent run, and each algorithm/hyperparameter combination
(Logistic Regression, Random Forest, HistGradientBoosting) is a nested run with its params,
metrics and model. The best model is registered as `suspicious-login-classifier` with the
alias **champion**.

**3. Serve the model**

```bash
uvicorn cyber_pipeline.api:app --port 8000
# http://localhost:8000/docs  -> try POST /predict with the built-in example
```

| Endpoint | Purpose |
|---|---|
| `POST /predict` | Score 1–1000 events and return probability + flag |
| `GET /health` · `GET /model-info` | Liveness and the loaded model's version, metrics and MLflow run |
| `POST /reload` | Hot-swap to a newly trained model (called by Airflow after retraining) |
| `GET /metrics` | Prometheus metrics |

**4. Orchestrate with Airflow** (install separately, see `requirements-airflow.txt`)

```bash
export AIRFLOW_HOME=~/airflow
export AIRFLOW__CORE__DAGS_FOLDER=$(pwd)/dags
airflow standalone          # UI at http://localhost:8080
# or run one DAG execution in the terminal:
airflow dags test cyber_etl_mlops_pipeline 2026-09-27
```

The DAG runs the three extracts in parallel, then `transform_and_load` →
`train_and_register` → `reload_api`, with automatic retries.

**5. Monitoring stack (Docker)**

```bash
docker compose up -d --build     # API :8000, MLflow :5000, Prometheus :9090, Grafana :3000 (admin/admin)
```

Grafana auto-loads the **Suspicious Login Model – Monitoring** dashboard. It shows request
rate, p50/p95 latency, predictions by label, share flagged as suspicious, the score
distribution (a drift check) and HTTP errors. `monitoring/alert_rules.yml` defines alerts for
API down, prediction errors, slow predictions and a drift in the flag rate.

**6. Tests**: `pytest -q`

## CI/CD (GitHub Actions)

`.github/workflows/ci-cd.yml` runs on every push/PR, weekly (scheduled retrain) and on demand:

1. **test**: ruff lint + pytest.
2. **train**: full ETL + training. The run fails if ROC-AUC < 0.80 (quality gate). The model and pipeline log are uploaded as artifacts.
3. **deploy** (main branch only): builds the serving image with the new model, pushes it to GitHub Container Registry (`ghcr.io/<owner>/<repo>/model-api`) and smoke-tests it.

## Results (local run, 300,000 events)

| Model | ROC-AUC | F1 |
|---|---|---|
| Logistic Regression (C=0.1) | 0.945 | 0.722 |
| Random Forest (depth 16) | 0.954 | 0.782 |
| **HistGradientBoosting (lr 0.05), champion** | **0.955** | **0.808** |

Time-based split: trained on the oldest 80% of events, tested on the newest 20%.

## Logging

Every stage logs to the console and to `logs/pipeline.log` (rotating), including start/finish
timings, row counts per batch, rows removed during cleaning, and full tracebacks on failure.
The API logs each scoring request and exposes counters and histograms for Prometheus.

## Switching to PostgreSQL or S3

```bash
pip install psycopg2-binary
export WAREHOUSE_DB_URL=postgresql+psycopg2://user:pass@localhost:5432/warehouse
```

No code changes are needed because every database operation uses SQLAlchemy. The Parquet copy
in `data/processed/` can be pushed to S3 with `aws s3 cp` or `boto3`.
